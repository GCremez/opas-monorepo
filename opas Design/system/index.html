Design Principles & Voice

Five product principles grounded in the design-principles skill, visual-critique composite, and content-strategy skill. Every screen is tested against these before shipping.

01

Clarity over cleverness

Every screen must be usable by someone with intermediate English and zero knowledge of Finnish administrative systems. No jargon, no assumptions. Miller's Law: keep 7±2 items per screen, no more.

02

Action-first hierarchy

The most important thing is what to do next — always the most prominent element. Follows the visual-hierarchy and von Restorff effect skills: the primary action should be visually unique.

03

One thumb, one tap

Every core action is reachable with the thumb on a 6.1" screen. The scan button is permanently in the bottom nav. Follows Fitts's Law: bigger targets closer to the thumb = faster interaction.

04

Calm & trustworthy

Users arrive stressed. The interface must feel solid, predictable, reassuring — never flashy. Hick's Law: fewer choices per screen reduces decision time and anxiety.

05

Respect the data

Government correspondence is sensitive. Design communicates security through restraint: clear visual boundaries around personal content, transparent loading states, no unnecessary data exposure.

Voice & Tone

Write in plain, direct English. Short sentences. Lead with the action or deadline. Never use bureaucratic language to explain bureaucratic language. Labels are concise nouns. Follows ux-writing skill: every word earns its place.

Information Architecture

Five core sections: Home (dashboard + deadlines), Documents (scan history), Scan (camera), Guides (walkthroughs), Account (settings). Follows information-architecture skill: card-sorted navigation, 5 ± 2 top-level items. Navigation-patterns skill: bottom tab bar with a visually distinguished primary action.

Token Architecture

Three-tier token system from the design-token skill. Components never reference raw values. Themes override Layer 2 only.

Layer 1 Global primitives

Raw atomic values — palette hexes, font stacks, unit, breakpoints. These are theme-agnostic and never change.

/* Primitives */ --color-black: #000000; --color-charcoal: #3c3c3c; --color-white: #f5f5f7; --color-mint: #92d9bb; /* Font stacks */ --font-lufga: 'Lufga', 'Inter', system-ui, sans-serif; --font-inter: 'Inter', system-ui, sans-serif; --font-jetbrains: 'JetBrains Mono', ui-monospace, monospace; /* Unit */ --unit: 4px; /* Safe areas (mobile) */ --safe-top: env(safe-area-inset-top, 0px); --safe-bottom: env(safe-area-inset-bottom, 0px);

Layer 2 Semantic aliases

Purpose-driven — what themes override. Mapped from primitives to functional roles.

/* Surface tokens */ --bg: var(--color-black); --surface: var(--color-charcoal); --fg: var(--color-white); --accent: var(--color-mint); /* Spacing */ --space-inset: 16px; --space-stack: 16px; --space-inline: 12px; /* Safe areas */ --safe-top: env(safe-area-inset-top, 0px);

Layer 3 Component-scoped

Bound per component. Reference semantic tokens only.

/* Button */ --btn-min-height: 44px; --btn-radius: var(--radius-10); --btn-primary-bg: var(--accent); /* Bottom sheet */ --sheet-radius: var(--radius-16); --sheet-handle-width: 32px;

Accessibility audit

  • --fg on --bg: 15:1 → AAA ✓
  • --muted on --bg: 5.3:1 → AA ✓
  • --accent on --bg: 5.7:1 → AA ✓ (do not use for small text)
  • Non-color signals: every status also uses an icon or label — never color alone (accesslint rule)
  • Touch targets: min 44px × 44px per Fitts's Law — verified on every interactive element

Guidelines

  • One accent per screen, used 1–2 times max. The accent is a precision tool, not a decorative wash
  • Status colors as badges or inline indicators — never full backgrounds
  • Squint test: blur your eyes — hierarchy should still be clear (visual-hierarchy skill)
  • Follow aesthetic-usability effect: visually pleasing designs are perceived as more usable — but never at the cost of accessibility

Spacing types

  • Inset: internal container padding. Mobile: 16px inset for cards, 20px for page margins
  • Stack: vertical space between elements. Related: 12–16px. Sections: 32–48px
  • Inline: horizontal gap between inline elements (buttons, pills). Default: 8–12px
  • Touch cushion: extra padding inside interactive areas to meet 44px min target

Mobile micro-interaction spec

  • Button press: scale(0.97) + 150ms ease-out — tactile response
  • Tab switch: 250ms fade + slide — content layer beneath nav stays static
  • Bottom sheet: 300ms spring entrance — slides up from edge with handle indicator
  • Toast: 250ms slide-in from top, auto-dismiss after 4s (or explicit close)
  • Pull to refresh: 400ms spring — spinner appears, content resists then releases
  • Page transitions: 350ms slide — push new screen from right (iOS) or fade (Android)
  • Haptic feedback: light impact for button press, medium warning for alerts, success notification for completion

Doherty Threshold compliance

Every user-initiated action provides feedback within 400ms. Loading states >400ms show a skeleton or spinner. Transitions >500ms show a progress indicator with a cancel option when possible (loading-states skill, doherty-threshold skill).

Gesture patterns

  • Swipe left on document card: reveals "Archive" and "Delete" actions (iOS-style)
  • Swipe right on document card: marks as "Done" / changes status
  • Pull down: refresh document list (with haptic on release)
  • Long press on document: context menu (select, share, export)
  • Tap scan button: opens camera immediately — no second tap

Hick's Law — choices per screen

  • Bottom nav: 5 items ← 5 ± 2 (Miller's Law)
  • Document list actions: 3 max (view, deadline, archive)
  • Filter chips: 5 max per category
  • Settings sections: grouped into 7±2 clusters
  • Onboarding: 3–5 steps, one decision each

Loading states (Doherty Threshold)

  • 0–200ms: no feedback needed. Feels instant.
  • 200–400ms: subtle spinner or inline loading indicator (e.g. while decoding a document)
  • 400–2000ms: skeleton screen matching content layout — maintain user orientation
  • 2000ms+: progress bar with estimated time + graceful degrade messaging
  • Failure: inline error message with retry action. Never a blank screen.

State machine — every component has states

Error handling

  • Document scan fails: show inline error with specific reason ("Too dark", "Blurry", "Not a document") + retry button
  • Network error: bottom toast with offline indicator, cached content shown, action queue stored locally
  • Decoding error: text-level explanation ("We couldn't read this format"), alternative options (manual entry, try again, email to support)
  • Empty state: clear what to do next ("No documents yet — tap Scan to start") — follows empty-state pattern

Safe areas

  • Use env(safe-area-inset-top) and env(safe-area-inset-bottom) in CSS
  • Content must not render under the notch or home indicator
  • Bottom tab bar includes safe area padding
  • Top nav includes safe area padding for Dynamic Island
  • Full-screen camera view: content behind safe areas (camera preview)

Touch & interaction

  • Minimum 44×44px for all touch targets — verified in Fitts's Law calculator above
  • Active/pressed states on every interactive element
  • No hover-dependent interactions on mobile (hover → press)
  • 400ms response guarantee (Doherty Threshold) — skeleton or spinner for any wait
  • Error messages are specific, actionable, and placed inline near the relevant element

WCAG compliance (accesslint)

  • Text contrast: min AA (4.5:1) for body, AAA (7:1) preferred for primary text
  • Non-text contrast: 3:1 for icons, borders, and focus indicators
  • Touch target minimum: 44×44px (exceeds WCAG 2.2 24×24px AA target)
  • Focus indicators: visible keyboard focus for all interactive elements
  • No information conveyed by color alone — every status also uses icon + label
  • Semantic HTML: <button> for actions, <nav> for navigation, ARIA labels where needed
  • Respects prefers-reduced-motion for vestibular sensitivity

Internationalization (i18n)

  • Design accommodates Finnish, Swedish, and English text
  • All labels and copy stored as tokenized strings — never hardcoded in components
  • Layout handles text expansion (Finnish compound words can be 2–3× English length)
  • RTL not a current requirement but should not break layouts
